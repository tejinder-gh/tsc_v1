# T-012 — Establish production-enforced rate limiting for public submission endpoints

**Source finding:** AUDIT_REPORT.md CTO-05 | Severity: P1 | Class: SUBOPTIMAL
**Assigned tier:** SENIOR + FOUNDER/OPS
**Effort estimate:** 1h configuration on Vercel, or a separately approved distributed-store build | **Sequence:** requires deployment-target decision; before T-013

## WHAT
Decide and prove the production rate-limit enforcement point before writing application code. For a Vercel deployment, configure a Vercel WAF rate-limit rule for `POST /api/lead` and `POST /api/newsletter/subscribe`, keyed by the platform-provided client IP. For any other horizontally scaled/serverless host, select and explicitly approve a durable shared rate-limit store or equivalent edge control. An in-memory `Map` may support local tests but cannot close this production finding because limits reset per instance and deployment.

## WHY
While both `/api/lead` and `/api/newsletter/subscribe` have honeypot fields and 32KB body size limits, an attacker running a simple curl loop bypasses the honeypot entirely. Without rate limiting, a single bot can exhaust Zapier webhook quotas, flood the inbox, and drive up API bills in minutes.

## SCOPE — DEPLOYMENT CONTROL
IN:
- Production deployment configuration and a non-secret evidence record of the active rule: endpoint match, HTTP method, window, threshold, action, and verification time.
- If the deployment target is not Vercel, a follow-up implementation ticket naming the approved shared enforcement layer and its costs.

OUT:
- `app/api/**`, `lib/schemas.ts`, and a process-local in-memory limiter. Do not represent application-memory state as a production DDoS or quota-control boundary.

## ACCEPTANCE CRITERIA
- [ ] AC1: The production host and enforcement layer are named; the client-IP header is trusted only when supplied/overwritten by that host.
- [ ] AC2: Both public POST routes have an active shared rate rule with an explicit threshold/window and a 429 response policy.
- [ ] AC3: A live non-destructive test proves requests below the threshold pass and the next request receives 429; the rule is then removed or allowed to expire if a temporary test rule was used.
- [ ] AC4: The evidence record contains no visitor IPs, webhook URL, or secrets.

## TEST PLAN
1. Record the host decision and proposed rule without changing production.
2. Obtain action-time approval before changing firewall or shared-service configuration.
3. Apply the rule and run the non-destructive threshold test against the intended environment.
4. Record the observed status codes and remove any temporary test artefacts.

## CONSTRAINTS
- Do not accept a process-local limiter as evidence that a serverless or multi-instance deployment is protected.
- Do not infer trusted proxy headers on a host that does not overwrite them.
- A production configuration change requires action-time user approval.

## ROLLBACK
Revert or delete the named deployment rule through the host control plane.

## BLOCKED PROTOCOL
If the deployment host or shared enforcement layer is unknown, status → REQUIRES USER. Do not fall back to an in-memory implementation and call the P1 finding closed.
