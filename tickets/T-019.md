# T-019 — Classify workflow trigger outcomes truthfully

**Source finding:** AUDIT_REPORT.md §F-04 | Severity: P1 | Class: BROKEN
**Assigned tier:** SENIOR
**Effort estimate:** 3.0 hours | **Sequence:** after T-016

## WHAT

Correct the dashboard workflow console so it never claims a lead was delivered or a context query succeeded when no delivery/query occurred. Keep the existing lead trigger as a simulation only: it may validate and display a test payload, but its machine-readable state and displayed text must say `simulated`/`not_delivered`, never `delivered` or “queued for webhook delivery.” When Second Brain database search fails, return a non-success unavailable result with a safe generic message; do not return `ok: true`, mock registry data as search results, or the raw database error. Update the console language and tests to render these states accurately.

## WHY

Operators are being given false operational confirmation. That leads to missed leads and unsafe incident decisions, and it undermines the public site’s trust-first positioning.

## SCOPE — FILES

IN:
- `app/dashboard/actions.ts` — change only simulated-lead and Second Brain failure result contracts; preserve authorization guard calls.
- `app/dashboard/actions.test.ts` — assert exact truthful result semantics for both success simulation and database-unavailable paths.
- `app/dashboard/workflows/workflow-console.tsx` — replace misleading lead/RAG copy and ensure result UI labels a simulation or unavailable outcome without showing raw database errors.
- `app/dashboard/workflows/page.tsx` — change page-level “live”/delivery wording if needed to match the new contract.

OUT:
- `app/api/lead/route.ts` — do not call the real endpoint from this manual trigger; T-021 owns its logging behavior.
- Webhook, CRM, database, or environment configuration — do not send real leads or make a live DB connection.
- Scheduler and inbound-SMS behavior — retain their existing mechanics; do not broaden this ticket into a general automation rewrite.
- `lib/second-brain/**` — do not change repository/database code; only handle its errors at this operator boundary.

## ACCEPTANCE CRITERIA (testable, binary)

- [x] AC1: A non-honeypot `triggerSimulatedLead()` result contains an explicit simulation state and `delivered: false`; it contains no `status: "delivered"` and no wording that says it queued/sent a webhook request.
- [x] AC2: The simulated lead path does not call `fetch`, `/api/lead`, or any webhook client; add a test assertion if a callable seam exists.
- [x] AC3: A context-repository failure yields `ok: false` (or an equally unambiguous unavailable state), a safe operator-facing message, and no `dbError` field/raw error text.
- [x] AC4: The workflow console visibly labels the lead tool as a simulation and the unavailable context result as unavailable; it no longer calls either output “live delivery” or live DB telemetry.
- [x] AC5: Existing authorized scheduler, inbound-simulation, and catalog-diagnostic tests remain passing.

## CONSTRAINTS

- Keep server-action return values serializable.
- Preserve the existing visualization and interaction layout; this is correctness copy/state work, not a redesign.
- Do not expose stack traces, connection strings, SQL errors, or environment-specific messages to the browser.
- No new dependencies; TypeScript strict; no `any`.

## ROLLBACK

Revert the implementation commit. Do not restore the old `delivered: true` response unless the trigger is redesigned to actually submit to the webhook with explicit owner authorization and idempotency controls.

## BLOCKED PROTOCOL

If the UI relies on an undocumented result shape outside the scoped files, STOP and report the consumer. Do not silently preserve a misleading field just to avoid a consumer update.
