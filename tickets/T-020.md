# T-020 — Label dashboard state as configuration, not health

**Source finding:** AUDIT_REPORT.md §F-05 | Severity: P1 | Class: BROKEN
**Assigned tier:** INTERMEDIATE
**Effort estimate:** 2.0 hours | **Sequence:** after T-019

## WHAT

Replace dashboard labels that present static configuration as live, healthy, authorized, or operational telemetry. The overview may show configured clients, registered routes, enabled recipes, and local file-store counts, but it must describe them as configuration/registry state. It must not present a render timestamp as synchronization, or static strings as scheduler, inbound, lead, database, or IAM health. Add explicit “not verified”/“unavailable” presentation wherever a live probe does not exist.

## WHY

The dashboard currently lets an operator infer that customer-facing systems are healthy without a successful external call or scheduled run. Accurate state labels reduce operational mistakes and support credible sales demonstrations.

## SCOPE — FILES

IN:
- `app/dashboard/actions.ts` — revise the `DashboardMetrics` subsystem state model and static descriptions to distinguish configured/registered/unverified state.
- `app/dashboard/actions.test.ts` — update/add assertions for the revised state contract.
- `app/dashboard/page.tsx` — update all affected badges, labels, descriptions, and timestamp copy on the overview only.

OUT:
- `app/dashboard/workflows/**` — T-019 owns execution-console truthfulness; do not re-edit it here.
- Health-check endpoints, cron persistence, external monitoring, database probing, or live telemetry infrastructure — not authorized; do not simulate them.
- Marketing pages and journey demonstrations — T-023 owns modeled-claim labeling.

## ACCEPTANCE CRITERIA (testable, binary)

- [x] AC1: The overview page contains no `Live Observability`, `Live cross-system telemetry`, `Scheduler Healthy`, `IAM Authorized`, `Ready for live customer inquiries`, or equivalent health assertion not backed by a probe.
- [x] AC2: Each overview subsystem state is explicitly representable as configuration/registered/unverified (or unavailable), not `operational`/`active` solely from static code.
- [x] AC3: `lastUpdated` is either removed or labeled as the dashboard render/configuration-read time, not synchronization/telemetry time.
- [x] AC4: Counts such as configured recipes and registered endpoints remain visible, but their labels do not imply external delivery or authorization success.
- [x] AC5: The overview metrics tests assert the new state values and pass.

## CONSTRAINTS

- Preserve real static counts and useful operator navigation.
- Do not add fake green/red status lights, fetch external services, or add a monitoring dependency.
- Use existing design tokens/classes and accessible text; no visual redesign.

## ROLLBACK

Revert the implementation commit. Do not reintroduce health claims without adding evidenced probes in a separately approved ticket.

## BLOCKED PROTOCOL

If a specific state actually is backed by a verified runtime probe in code outside scope, STOP and report the source. Do not remove a proven signal, and do not assume one exists.
