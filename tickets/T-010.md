# T-010 — Code-split journey demonstration view and decouple bundle re-exports

**Source finding:** AUDIT_REPORT.md CTO-03 | Severity: P1 | Class: SUBOPTIMAL  
**Assigned tier:** SENIOR  
**Effort estimate:** 2.5h | **Sequence:** independent

## WHAT
Optimize the homepage and marketing layout JavaScript bundle by code-splitting the interactive demonstration view (`DemonstrationView.tsx`) and removing the direct re-export of `demonstration-config.ts` (111KB) and `opportunity-config.ts` (21KB) from `lib/journey/index.ts`. In `components/journey/JourneyHero.tsx`, load `DemonstrationView` lazily using `next/dynamic` with an accessible skeleton/loading state when `journey.stage === "solution"`. Update imports in components so that pages importing journey context types do not pull the heavy demonstration configuration into their initial chunks.

## WHY
The client JS bundle currently ships over 1.5MB of chunks because `demonstration-config.ts` (111KB of static scenarios) and `opportunity-config.ts` are statically bundled on initial page load via barrel re-exports in `@/lib/journey` and a hard import in `JourneyHero.tsx`. Visitors on 3G/4G mobile connections suffer noticeable hydration delay before interacting with the homepage, even though the demonstration view is only displayed when a user actively clicks through to the solution stage.

## SCOPE — FILES
IN:
- `components/journey/JourneyHero.tsx`
- `components/journey/demonstration/DemonstrationView.tsx`
- `lib/journey/index.ts`

OUT:
- `lib/journey/demonstration-config.ts` — do not touch the scenarios data or configuration contents.
- `lib/journey/opportunity-config.ts` — do not modify diagnostic opportunity matrix data.
- `components/journey/demonstration/SystemSpecRenderer.tsx`, `DecisionRouterRenderer.tsx`, `EducationalArtifactRenderer.tsx`, `PipelineStreamRenderer.tsx` — renderers remain intact.
- `app/(marketing)/page.tsx` — homepage structure unchanged.

## ACCEPTANCE CRITERIA
- [ ] AC1: `JourneyHero.tsx` dynamically imports `DemonstrationView` using `next/dynamic` with `ssr: false` (or client-only suspense boundary), deferring scenario payload loading until `journey.stage === "solution"`.
- [ ] AC2: A lightweight, accessible loading skeleton renders seamlessly while the dynamic demonstration component chunk loads.
- [ ] AC3: `lib/journey/index.ts` exports only journey types, context, and storage; direct `export * from "./demonstration-config"` is removed from the root barrel (consumers needing config import directly from `@/lib/journey/demonstration-config`).
- [ ] AC4: Initial page bundle size for `/` is measurably reduced in `.next/static/chunks/` inspection after `npm run build`.
- [ ] AC5: All 307 tests pass (`npm test`).
- [ ] AC6: Complete interactive flow (Intent Selection → Problem Input → Context → Opportunity → Demonstration) functions identically in the browser without hydration mismatch.

## TEST PLAN
1. Run `npm run build` and inspect generated route chunk sizes; verify the demonstration bundle is isolated in a separate lazy chunk.
2. Run `npm test` to ensure journey context and demonstration unit tests pass without error.
3. Start local server (`npm run dev` or `npm run start`) and click through the full journey from home hero down to demonstration view, verifying smooth loading without layout shift.

- Keep renderers modular.
