# T-016 — Restrict dashboard actions to approved Clerk operators

**Source finding:** AUDIT_REPORT.md §F-01 | Severity: P0 | Class: BROKEN
**Assigned tier:** SENIOR
**Effort estimate:** 3.0 hours | **Sequence:** independent; must land before every other dashboard ticket

## WHAT

Change dashboard authorization from “any authenticated Clerk user” to an explicit server-side allowlist of Clerk user IDs. Every dashboard server action and server-rendered dashboard data load that already calls `assertOperatorAuthenticated()` must reject a signed-in user who is not in `DASHBOARD_OPERATOR_USER_IDS`. The local bypass is permitted only when both `NODE_ENV === "development"` and `ALLOW_DEV_OPERATOR_AUTH === "true"`; it must never activate in production. An unset or whitespace-only allowlist must fail closed outside that exact local-development condition.

## WHY

The dashboard can approve drafts, toggle flows, run scheduler work, and expose operational details. Authentication alone is not authorization; current code gives that capability to every Clerk account. This is the release-blocking access-control defect.

## SCOPE — FILES

IN:
- `app/dashboard/auth-guard.ts` — parse and enforce the comma-separated allowlist; retain `assertValidClientId()` behavior.
- `app/dashboard/actions.test.ts` — replace the current “any user is an operator” assertion and add authorization regression coverage for existing actions.
- `.env.example` — add placeholder-only documentation for `DASHBOARD_OPERATOR_USER_IDS` and correct the dashboard-auth comment.

OUT:
- `middleware.ts` — it may continue to require sign-in; this ticket adds server-side authorization and must not attempt a Clerk proxy migration.
- `app/dashboard/team/**`, `app/invite/**`, and `lib/team/**` — handled by T-017; do not try to make the fake roles real here.
- Clerk Dashboard configuration, real user IDs, organizations, and roles — external owner-only configuration; never invent IDs.
- Any public marketing route or API route — no behavior change is authorized there.

## ACCEPTANCE CRITERIA (testable, binary)

- [x] AC1: With `NODE_ENV=production`, `DASHBOARD_OPERATOR_USER_IDS=user_allowed`, and Clerk returning `user_allowed`, `assertOperatorAuthenticated()` resolves `{ userId: "user_allowed" }`.
- [x] AC2: With the same production environment and Clerk returning `user_not_allowed`, `assertOperatorAuthenticated()` rejects with an error matching `Unauthorized` or `Forbidden`; it must not return a user object.
- [x] AC3: With production environment and missing/blank `DASHBOARD_OPERATOR_USER_IDS`, a signed-in Clerk user is rejected.
- [x] AC4: `ALLOW_DEV_OPERATOR_AUTH=true` returns `dev_operator` only with `NODE_ENV=development` and no Clerk user; the identical flag under `NODE_ENV=production` rejects.
- [x] AC5: At least one mutating action (`toggleFlow`) is proven rejected for an authenticated but unallowlisted user and permitted for an allowlisted user; existing invalid-client protection remains covered.
- [x] AC6: `.env.example` contains no real Clerk user ID and documents comma-separated values plus the fail-closed production behavior.

## TEST PLAN

1. Run `npm test -- app/dashboard/actions.test.ts`; expect all authorization and existing workflow tests to pass.
2. Run `npm test`; expect exit 0.
3. Run `npm run lint` and `npx tsc --noEmit`; record results. Lint may still fail until T-022, but this ticket must not introduce errors in its scoped files.
4. Do **not** test against a real Clerk account or deploy without owner approval. Record that live allowlist verification remains an external release gate.

## CONSTRAINTS

- Follow the existing `assertOperatorAuthenticated()` call pattern; do not duplicate access checks through individual actions.
- No new dependency, database table, Clerk Organization, role, or client-visible access-control UI.
- Treat environment input as untrusted: trim entries, ignore empty items, and do exact ID comparison.
- Keep TypeScript strict; no `any`, no secret/user-ID logging.

## ROLLBACK

Revert the single implementation commit. Do not remove the production environment allowlist as a workaround; if the configured owner ID is wrong, correct that external configuration under owner control.

## BLOCKED PROTOCOL

If the deployed app uses a different authorization source than Clerk user IDs, STOP. Report the actual source and why it conflicts with this ticket; do not silently substitute Organization roles or an email allowlist.
