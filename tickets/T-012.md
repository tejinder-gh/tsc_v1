# T-012 — Add IP-based sliding-window rate limiting to public lead and newsletter APIs

**Source finding:** AUDIT_REPORT.md CTO-05 | Severity: P1 | Class: SUBOPTIMAL  
**Assigned tier:** SENIOR  
**Effort estimate:** 2.5h | **Sequence:** independent

## WHAT
Implement an in-memory, sliding-window rate limiter in `lib/rate-limit.ts` (zero dependencies, self-cleaning cache) and integrate it into `POST /api/lead` and `POST /api/newsletter/subscribe`. Requests exceeding threshold limits (e.g., 10 submissions per minute per IP on `/api/lead`; 5 requests per minute per IP on `/api/newsletter/subscribe`) will be throttled with HTTP 429 Too Many Requests and standard `Retry-After` headers, protecting downstream Zapier/Make webhooks and CRM services from quota burn and denial-of-service spam loops.

## WHY
While both `/api/lead` and `/api/newsletter/subscribe` have honeypot fields and 32KB body size limits, an attacker running a simple curl loop bypasses the honeypot entirely. Without rate limiting, a single bot can exhaust Zapier webhook quotas, flood the inbox, and drive up API bills in minutes.

## SCOPE — FILES
IN:
- `lib/rate-limit.ts`
- `lib/rate-limit.test.ts`
- `app/api/lead/route.ts`
- `app/api/newsletter/subscribe/route.ts`

OUT:
- `app/api/inbound/route.ts` — Twilio webhooks are protected by Twilio cryptographic signatures; do not rate-limit inbound carrier SMS.
- `app/api/v1/relay/route.ts` — relay is protected by HMAC-SHA256 signatures; do not alter.
- `app/api/cron/route.ts` — cron is protected by Bearer secret; do not alter.
- `lib/schemas.ts` — validation schemas remain untouched.

## ACCEPTANCE CRITERIA
- [ ] AC1: `lib/rate-limit.ts` provides a deterministic sliding-window rate limiter helper `checkRateLimit(req: Request, options: { limit: number; windowMs: number })`.
- [ ] AC2: Client IP is reliably extracted from `x-forwarded-for` (first non-internal IP) or `x-real-ip`, with a graceful fallback.
- [ ] AC3: `POST /api/lead` enforces a maximum of 10 requests per 60 seconds per IP; exceeding requests receive HTTP 429 `{ ok: false, error: "Too many requests. Please wait a moment." }` with a `Retry-After` header.
- [ ] AC4: `POST /api/newsletter/subscribe` enforces a maximum of 5 requests per 60 seconds per IP; exceeding requests receive HTTP 429 with `Retry-After`.
- [ ] AC5: In-memory sliding window purges stale IP records periodically to prevent memory leaks.
- [ ] AC6: Unit tests in `lib/rate-limit.test.ts` thoroughly test window reset, limit enforcement, and IP parsing.
- [ ] AC7: `npm test` passes all tests cleanly (307 existing + new rate limit tests).
