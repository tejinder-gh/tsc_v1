# T-013 — Add a truthful architecture-request capture flow to the demonstration

**Source finding:** AUDIT_REPORT.md CPO-01 / CFO | Severity: P1 | Class: MISSING  
**Assigned tier:** SENIOR  
**Effort estimate:** 3h | **Sequence:** after T-010, T-012, and T-015

## WHAT
Add a high-intent "Request this architecture" action to the completion state of the interactive demonstration. It captures a name, work email, business name, and the minimal deterministic scenario identifiers needed for staff follow-up. It does not claim that a document is generated or emailed: the current API forwards a lead to a webhook and has no blueprint-delivery provider.

## WHY
The current demonstration has only scenario controls and return navigation; it has no capture or booking action. A low-commitment request gives a prospect a truthful way to ask for a human follow-up without overstating automated fulfilment. The audit's conversion and revenue estimates are hypotheses, not acceptance criteria.

## ACCEPTANCE CRITERIA
- [ ] AC1: A prominent "Request this architecture" action renders only after a visitor completes a demonstration. It does not imply automatic email, attachment, or document delivery.
- [ ] AC2: Clicking the button opens an accessible modal with fields: Full Name, Work Email, Business Type / Name, and a hidden honeypot `website` field.
- [ ] AC3: Form submission sends `lead_source: "demonstration_architecture_request"` and a schema-validated `journey_context: { opportunityId, scenarioId, scenarioTitle }`. Raw `freeformProblem` and scenario data payloads are never submitted.
- [ ] AC4: Displays an inline success confirmation that truthfully says the request was received and a person will follow up, without resetting the journey state.
- [ ] AC5: Form uses accessible ARIA dialog roles, focus trap, and Escape key dismissal.
- [ ] AC6: Route and client-helper tests prove the validated context is forwarded and unsupported fields are rejected or stripped by the declared schema. `npm test` passes with no regression from the pre-ticket baseline; build status distinguishes environment blocks from source errors.

## TEST PLAN

5. Verify the truthful success alert renders and the modal can be dismissed cleanly.
