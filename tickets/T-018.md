# T-018 — Enforce production database certificate verification

**Source finding:** AUDIT_REPORT.md §F-03 | Severity: P1 | Class: BROKEN
**Assigned tier:** SENIOR
**Effort estimate:** 3.0 hours | **Sequence:** independent

## WHAT

Make certificate verification non-bypassable whenever `NODE_ENV` or `VERCEL_ENV` is `production`. Both the web runtime pool and the administrative pool must use `{ rejectUnauthorized: true }` in production, even if `SECOND_BRAIN_DB_SSL_REJECT_UNAUTHORIZED=false` is supplied. Localhost and explicit development/test behavior may remain as currently intended, but an unsafe production override must throw a clear configuration error instead of silently downgrading TLS.

## WHY

The current resolver explicitly accepts an insecure production override and the admin client always disables verification. Database credentials and private context traffic must not be vulnerable to a configuration-driven TLS downgrade.

## SCOPE — FILES

IN:
- `lib/second-brain/db/client.ts` — correct production precedence and expose/reuse the safe resolver as needed.
- `lib/second-brain/admin/lifecycle.ts` — consume the same safe production TLS behavior instead of hard-coding `rejectUnauthorized: false`.
- `lib/second-brain/__tests__/database-ssl.test.ts` — replace the unsafe-production expectation and cover both production discriminators.
- `.env.example` — document the variable only if it remains supported for non-production; explicitly prohibit unsafe production configuration.

OUT:
- Database URLs, Neon project settings, certificate files, migrations, schema, and real credentials — no live infrastructure change.
- `lib/second-brain/__tests__/lifecycle.test.ts` — do not rewrite lifecycle behavior unless a minimal test seam is demonstrably required; explain any addition before making it.
- API authentication/authorization — handled separately and must not be changed.

## ACCEPTANCE CRITERIA (testable, binary)

- [x] AC1: For a remote URL with `NODE_ENV=production` and `SECOND_BRAIN_DB_SSL_REJECT_UNAUTHORIZED=false`, the resolver either returns `{ rejectUnauthorized: true }` or throws a clear unsafe-production configuration error; it never returns `false` or `{ rejectUnauthorized: false }`.
- [x] AC2: AC1 also holds when only `VERCEL_ENV=production` is set.
- [x] AC3: A non-production remote URL may retain the documented override/default behavior, and localhost/`sslmode=disable` remains disabled only outside production.
- [x] AC4: The admin pool no longer contains a literal `rejectUnauthorized: false`; it follows the same production decision as the runtime pool.
- [x] AC5: The SSL unit test explicitly covers production false-override rejection/enforcement and passes.
- [x] AC6: No real database connection is made by unit tests.

## TEST PLAN

1. Run `npm test -- lib/second-brain/__tests__/database-ssl.test.ts`; expect exit 0.
2. Run `npm test`; expect exit 0.
3. Run `npm run lint` and `npx tsc --noEmit`; expect no new errors in scoped files.
4. Do not test against a live Neon database without owner approval. Record that a real connection smoke remains an external gate.

## CONSTRAINTS

- Reuse one resolver/predicate where practical so runtime and admin behavior cannot drift again.
- Production safety takes precedence over environment convenience. Do not use `NODE_TLS_REJECT_UNAUTHORIZED=0`, connection-string rewriting, or a blanket trust-all certificate setting.
- No new dependency and no plaintext URL/credential in tests, docs, or logs.

## ROLLBACK

Revert the implementation commit. If a production database then fails certificate validation, fix its CA/connection configuration; do not re-enable unverified TLS as a rollback shortcut.

## BLOCKED PROTOCOL

If the PostgreSQL driver’s SSL behavior conflicts with the ticket’s assumptions, STOP and cite the driver behavior and proposed minimal adaptation. Do not infer a certificate policy from a successful local connection.
