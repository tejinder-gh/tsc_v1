# T-021 — Minimize lead payload logging

**Source finding:** AUDIT_REPORT.md §F-06 | Severity: P1 | Class: BROKEN
**Assigned tier:** SENIOR
**Effort estimate:** 2.0 hours | **Sequence:** independent

## WHAT

Remove clear-text lead payload logging from the honeypot and missing-production-webhook branches. Replace it with a structured, PII-minimized event containing only operational metadata needed to diagnose the outcome (for example route/event name, branch/reason, and timestamp if the logger adds none). Update the privacy-page wording only as needed so it accurately describes the bounded operational logging behavior; do not make legal/compliance guarantees.

## WHY

Lead records include names, emails, company names, and free-text notes. Writing whole records to hosting logs is unnecessary PII retention and contradicts the site’s transit-only/purged-log message.

## SCOPE — FILES

IN:
- `app/api/lead/route.ts` — replace the two full-record log statements with PII-minimized operational events.
- `app/api/lead/route.test.ts` — add assertions that no raw lead values are passed to `console.warn`/`console.error` in those branches while response semantics remain unchanged.
- `app/(marketing)/legal/privacy/page.tsx` — make the precise logging/retention sentence truthful if it currently says logs are purged or transit-only without qualification.

OUT:
- Lead schema, webhook payload, destination CRM, analytics, and form UI — do not remove information from a valid delivery or alter lead-capture behavior.
- Other application logs — do not launch a repository-wide logging refactor.
- Legal review, retention schedules, consent platform, PIPEDA/PHIPA certification, or policy approval — require owner/legal review and are not completeable by this ticket.

## ACCEPTANCE CRITERIA (testable, binary)

- [x] AC1: A honeypot submission returns its existing safe success response and never logs `name`, `email`, `company`, `notes`, or the serialized lead object.
- [x] AC2: A production request with no `LEAD_WEBHOOK_URL` returns the existing 503 response and never logs values from the lead record.
- [x] AC3: The retained logs identify the event/branch without customer-provided values or a JSON serialization of the record.
- [x] AC4: The privacy page no longer asserts that all transit logs are purged if the application retains any operational event logging; it uses scoped, non-legal-advice language.
- [x] AC5: Valid webhook forwarding retains the complete schema-approved record and existing lead-route tests pass.

## TEST PLAN

1. Run `npm test -- app/api/lead/route.test.ts`; expect exit 0 and the new log-argument assertions to pass.
2. Run `npm test`; expect exit 0.
3. Run `npm run lint` and `npx tsc --noEmit`; expect no scoped-file errors.
4. Do not post a real lead or inspect production logs without owner approval.

## CONSTRAINTS

- Treat every lead field as sensitive, including company and free-text notes.
- Do not hash emails as a substitute unless a documented operational need and salt policy exists; none is authorized here.
- Do not change HTTP status contracts or webhook payload shape.
- No dependency additions and no legal certification language.

## ROLLBACK

Revert the implementation commit. Do not restore PII logging to diagnose a webhook issue; use non-customer test payloads and approved observability instead.

## BLOCKED PROTOCOL

If an external logging contract is discovered that requires a field this ticket removes, STOP and document the exact contract and retention owner. Do not retain PII by default.
