# T-009 — Enforce production TLS certificate verification in database client

**Source finding:** AUDIT_REPORT.md CTO-02 | Severity: P1 | Class: SUBOPTIMAL  
**Assigned tier:** SENIOR  
**Effort estimate:** 2h | **Sequence:** after T-008; before any production Second Brain database use

## WHAT
Create one shared SSL-policy helper and use it for both the least-privilege runtime pool and the administrative pool. Production must always verify the database certificate chain. Development and test may omit TLS configuration where local Postgres does not use it. A configuration value must never weaken certificate verification in production.

## WHY
Disabling certificate verification (`rejectUnauthorized: false`) leaves TLS connections to hosted databases (Neon, RDS, Supabase) vulnerable to man-in-the-middle (MITM) attacks and credential eavesdropping on public or untrusted network hops. In production, database pools handling machine agent credentials and IAM state must verify the database server's identity.

## ACCEPTANCE CRITERIA
- [ ] AC1: When `NODE_ENV === "production"` or `VERCEL_ENV === "production"`, both pools configure `ssl: { rejectUnauthorized: true }`.
- [ ] AC2: No environment variable can set `rejectUnauthorized: false` in production. A development-only TLS opt-in may be documented in `.env.example` if needed.
- [ ] AC3: Development and test environments continue to function without requiring an external CA bundle.
- [ ] AC4: The new SSL-policy tests cover production, development, test, and an attempted production weakening override for both pool consumers.
- [ ] AC5: `npm test` passes with no regression from the pre-ticket baseline.
- [ ] AC6: `npm run build` and `npm run lint` pass without errors.
